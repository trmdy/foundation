# Render spike — is Foundation's render contract achievable?

Decides how honest `docs/SPEC.md` §5 and `docs/PRD.md` success criterion 3 can be:
"renders are a pure function of (document, render config)" and "identical projection +
render config on two different machines produce bit-identical layout reports and
pixel-identical renders." This spike answers the run-to-run half directly (one machine)
and hands a ready-to-use protocol for the cross-machine half (needs a second box).

## What's here

- `fixtures/sample.fdn.html` — a small, self-contained design document: type scale
  (system font stack + a `@font-face` loading a locally-subset Georgia woff2, embedded
  as a `data:` URI so there's no network dependency), a flex card row, a CSS grid of
  color swatches, borders/radius/box-shadow, a 24x24 inline `data:image/png` icon (hand
  -encoded PNG, not fetched), and every color/space/radius value expressed as a CSS
  custom property (token layer). No external URLs, no scripts, nothing that touches the
  network — matches D1's determinism requirement.
- `run.ts` — the harness (`pnpm spike:render`). Launches pinned Chromium via Playwright
  with a determinism-maximizing flag set, renders the fixture at three fixed viewports
  (390x844, 834x1194, 1440x900), **twice each in fresh browser contexts**, and compares:
  byte-identity of the PNGs (falling back to `pixelmatch` + an exact-byte diff scan when
  they differ), and exact equality of a `getBoundingClientRect()` report over every
  `[id]` element.
- `RESULTS.md` — generated by `run.ts`. Per-viewport verdict, the exact Chromium
  version/build and flag set used, an honest-assessment section, and the cross-machine
  protocol (below).
- `out/` — generated (gitignored except the fixture): `run1.png`/`run2.png`/`diff.png`
  per viewport, `layout-run1.json`/`layout-run2.json`, and `hashes.json` (sha256 of
  every artifact, for the cross-machine diff).

## How to run

```sh
pnpm install
pnpm exec playwright install chromium   # once, or after a playwright version bump
pnpm spike:render                       # writes spikes/render/RESULTS.md + out/
pnpm typecheck                          # spikes/**/*.ts, strict
```

Re-running is safe — `out/` is wiped and rebuilt each time.

## The finding, short version

On this machine, run-to-run, every viewport came back **bit-identical** (byte-equal
PNGs) and **layout-identical** (exact float equality on every `getBoundingClientRect()`
field) across two independent browser contexts. See `RESULTS.md` for the actual numbers,
flag set, and Chromium build this was verified against — regenerate it any time with
`pnpm spike:render` rather than trusting a stale copy.

That result does **not** extend to cross-machine by itself. The honest-assessment
section in `RESULTS.md` lays out why (font rasterization backend differs by OS — CoreText
vs FreeType vs DirectWrite — even with the same embedded font file; CPU/SIMD floating-
point paths differ across architectures even with GPU rasterization forced off) and
recommends the contract Foundation's spec should actually make: **layout-identical**
as a hard guarantee, **pixel-identical within a reported near-zero tolerance** rather
than byte-identical, cross-machine.

## Cross-machine comparison (do this on a second machine)

`RESULTS.md`'s "Cross-machine protocol" section has the exact commands. Summary:

1. Copy this repo (or just `spikes/render/` plus the root `package.json` /
   `pnpm-lock.yaml` / `tsconfig.json`, since typecheck includes `spikes/**`) to a second
   machine over the tailnet (`rsync`/`scp`, hostnames via `tailscale status`).
2. On machine B: `pnpm install && pnpm exec playwright install chromium && pnpm spike:render`.
   The pinned `playwright` version in `package.json` (`^1.62.0`, exact via the lockfile)
   is what makes "same Chromium build on both machines" true without manual version
   pinning.
3. Pull `spikes/render/out/hashes.json` back from machine B and diff it against
   machine A's. Matching PNG hashes = bit-identical cross-machine (the strong result);
   matching layout hashes but differing PNG hashes = layout held, rasterization didn't
   (the predicted, and per the recommended contract, *acceptable* outcome); differing
   layout hashes = a real cross-build/cross-platform layout bug worth chasing.

No human judgment call is required to run the comparison — `hashes.json` makes it a
`diff`. Human judgment is only needed to decide, once real hardware data exists across
enough machines, whether the "acceptable divergence" the honest-assessment section
predicts is actually small enough in practice to ship the tolerance-based contract as
written, or whether it needs tightening (e.g. mandate the same OS across all render
workers, not just the same Chromium build).
